


Архитектурная спецификация комплекса тестирования (КПСУ)
1. Назначение системы
Комплекс предназначен для проверки и моделирования бортовой аппаратуры (блоков БКД, ЯПС, ЯКП, ЯАЗ, ЯЛК, ЯВП) в составе ракетной ступени. Система обеспечивает:

Циклический опрос блоков с частотой 100 Гц.

Синхронизацию времени с точностью < 1 мкс (PTP).

Эмуляцию отсутствующих блоков (математические модели, заглушки).

Выполнение циклограмм (последовательности команд во времени).

Логирование всех данных с временными метками.

Графический интерфейс для визуализации и ручного управления.

Возможность работы как с реальным ЯЛС (коммутатором), так и в режиме полной эмуляции.

2. Архитектурная модель
Система построена по принципу Master‑Slave, где Master – единственное real‑time ядро, а Slave – либо реальные физические блоки, либо их программные эмуляторы.

Физическое развёртывание: единый бинарный файл на одном компьютере (Linux с PREEMPT_RT). Все компоненты работают в рамках одного процесса, но разделены на потоки с разными приоритетами.

2.1. Компоненты и их ответственность
Компонент	Поток	Приоритет	Ответственность
Master	1	Высокий (SCHED_FIFO)	Генерация тактов 100 Гц, формирование команд для блоков, обработка ответов, выполнение циклограммы, отправка данных в очереди для GUI/лога.
Сетевой слой	N (пул)	Высокий	Асинхронный приём/отправка UDP пакетов. В режиме эмуляции – вызов эмуляторов блоков. В реальном режиме – обмен с ЯЛС.
Эмуляторы блоков	В потоке сетевого слоя или отдельном	Высокий	Симуляция поведения блока: получение BKDRequest, выдача BKDResponse. Могут использовать простую логику или вызывать MATLAB DLL.
GUI	1	Обычный	Отображение состояния блоков (углы, пиро), приём команд от оператора, отправка команд Master через очередь.
Логгер	1	Низкий	Чтение из lock‑free очереди, запись в бинарный файл с PTP‑метками.
Менеджер моделей	Отдельный поток (по запросу)	Обычный	Загрузка MATLAB DLL, создание/уничтожение экземпляров, вызов model_step (по запросу от эмулятора).
2.2. Межпотоковое взаимодействие
Все обмены между потоками осуществляются через однопроизводительные однопотребительные (SPSC) lock‑free очереди (boost::lockfree::spsc_queue). Это исключает блокировки и гарантирует детерминизм.

Отправитель	Получатель	Тип очереди	Содержимое
Master	Сетевой слой	SPSC (Master → Network)	YVToYLSPacket (команда на отправку)
Сетевой слой	Master	SPSC (Network → Master)	YLSToYVPacket (ответ от ЯЛС или эмуляторов)
GUI	Master	SPSC (GUI → Master)	GuiCommand (установка маски, углов)
Master	GUI	SPSC (Master → GUI)	TickData (снимок состояния)
Master	Логгер	SPSC (Master → Logger)	TickData (для записи)
2.3. Режимы работы сетевого слоя
Режим реального ЯЛС: сетевой слой отправляет YVToYLSPacket (128 байт) на заданный IP:port реального ЯЛС, асинхронно ожидает ответ YLSToYVPacket (8192 байт).

Режим эмуляции: сетевой слой, не покидая процесса, вызывает массив эмуляторов блоков, собирает ответы и формирует YLSToYVPacket.

Переключение режима – статическое (задаётся при сборке через конфигурацию).

4. Протоколы и форматы данных
4.1. Протокол Master ↔ ЯЛС / эмуляторы
Запрос (128 байт): структура YVToYLSPacket (yls_index, command, drives[12][3], pyro_masks[12], reserved[42]).

Ответ (8192 байт): структура YLSToYVPacket (yls_index, command, drives[12][3], yaz_data[192], pyro_masks[12], ylk_data[192], yvp_data[648], reserved[7074]).

В поле reserved планируется разместить 8‑байтную временную метку (наносекунды от PTP) для точной привязки.

4.2. Внутренние структуры
BKDRequest (9 байт): для передачи команды одному блоку (используется только в эмуляции).

BKDResponse (95 байт): ответ от блока.

GuiCommand: команда от GUI (установка маски пиро, углов).

TickData: снимок состояния всех блоков для GUI и логгера.

4.3. Формат логов
Бинарный поток, где каждая запись – это структура TickData с добавленными метаданными (номер такта, временная метка). Для последующего анализа будут написаны конвертеры в CSV, PCAP.

5. Конфигурация системы
Все параметры (количество блоков, период цикла, IP/порт ЯЛС, режим эмуляции/реального ЯЛС, параметры эмуляторов) задаются на этапе сборки через переменные CMake. Из них генерируется заголовочный файл config_generated.h, который затем компилируется в бинарник.

Преимущества:

Отсутствие парсинга конфигурации во время выполнения.

Возможность оптимизаций компилятора.

Полная детерминированность.

Недостатки: требуется пересборка для изменения параметров. Для отладки допускается использование отдельного конфигурационного файла, но только в не‑real‑time частях (GUI, логгер).

6. План реализации по этапам
Этап 0: Прототип Master с циклом 100 Гц (выполнено)
Реализован Master с CycleTimer.

Добавлена заглушка DummyNetwork.

Очереди lock‑free работают.

Этап 1: Эмуляция блоков (текущий)
Реализовать SimpleEmulator для 12 блоков.

Реализовать EmulatedNetwork.

Подключить EmulatedNetwork в main.

Проверить, что мастер опрашивает все 12 блоков и получает ответы.

Замерить время обработки всех блоков, убедиться, что укладывается в 10 мс.

Этап 2: Реальный сетевой слой (RealYlsNetwork)
Написать класс, использующий Boost.Asio для асинхронной отправки/приёма.

Поддержать таймауты (через steady_timer).

Добавить возможность переключения между эмуляцией и реальным ЯЛС (статически).

Этап 3: PTP и временные метки
Настроить linuxptp на целевой машине.

Получать аппаратные метки времени через SO_TIMESTAMPING.

Включить временные метки в пакеты (использовать резервные поля).

Логировать временные метки.

Этап 4: Логирование
Реализовать асинхронный логгер: отдельный поток, читающий из lock‑free очереди.

Писать в бинарный файл структуры TickData.

Добавить вспомогательные утилиты для просмотра логов.

Этап 5: GUI
Создать отдельный поток для Qt.

Организовать обмен с Master через очереди.

Адаптировать старые виджеты для отображения данных.

Реализовать отправку команд (клики по пиро, ручное изменение углов).

Этап 6: Циклограмма
Разработать статическое описание событий (структуры TimelineEvent).

В Master перед каждым тактом проверять, не наступило ли событие, и обновлять уставки.

Для гибкости – генератор из Lua (внешний инструмент) создаёт C++ структуры на этапе сборки.

Этап 7: MATLAB интеграция
Создать интерфейс для загрузки DLL.

В MatlabEmulator вызывать model_step в отдельном потоке с контролем времени.

Если модель не укладывается в такт, использовать предыдущее значение.

Этап 8: Испытания и оптимизация
Запуск с реальным ЯЛС.

Измерение джиттера, потерь пакетов.

Оптимизация (привязка потоков к ядрам, изоляция CPU, настройки ядра).

7. Инструменты разработки и тестирования
IDE: Qt Creator (сборка через CMake).

Отладка: GDB, perf, Tracy (для real‑time трассировки).

Профилирование: perf, valgrind --tool=callgrind.

Анализ сети: Wireshark (фильтр ptp).

Unit‑тесты: Google Test (только для не‑real‑time частей).
